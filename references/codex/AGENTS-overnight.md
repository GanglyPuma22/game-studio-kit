# Overnight and production runs (Game Studio Kit)

When a prompt names an overnight, unattended, production or ledger-driven run, or hands you a production contract for a game project, read `skills/studio-director/references/overnight-run.md` in the installed kit in full before the first command; it carries the procedure, budgets, scope ladder and templates. There is no `studio` on PATH: run every command as `python <KIT>/scripts/studio.py <command>` with an explicit project or output root.
- The root session is the only desktop, GPU and provider owner and keeps only desktop and visual work. Everything text-only (proof mathematics, test triage, matrices, inventories, hashing, patch review) goes to a worker or a script, one deliverable per spawn; a worker never gets desktop, GPU or provider access.
- Never poll: `studio launch`, `studio batch` and `studio playtest` block for minutes and return one verdict, so the tool call that carries the command has to be told to wait for the whole run. Set the outer yield directive on that call (`// @exec: {"yield_time_ms": N}` in the Codex harness), sized from the bound that command enforces, because only `launch` has a `--timeout`: for `launch`, (`--timeout` in seconds plus 30) times 1000; for `batch`, and for `playtest --session driven` or a `handoff` with a non-zero `--max-minutes`, (`--max-minutes` times 60, plus 30) times 1000, where an omitted `--max-minutes` is 60 minutes; for an uncapped `playtest --session handoff --max-minutes 0`, the harness's maximum, the one case where a single sized `wait` after an early return is expected rather than a symptom; `playtest --session attended` is never waited for at all, and one later `playtest collect` completes it. A `yield_time_ms` passed inside the command does not set the directive, and without it the harness returns after its default outer yield of about 30 seconds, which is a harness default and not a host cap. A return before the verdict JSON therefore means the directive was missing or undersized, not that the run hung: the engine is still running, so never start a second one, and continue with a single `wait` sized to the time the command has left — never repeated short waits and never an empty `write_stdin`. `python <KIT>/scripts/studio.py batch --project <run> --plan <file>` is the blocking primitive that replaces a hand-rolled wait loop; separate `launch` calls are right only when a run's arguments depend on an earlier run's verdict or each run needs its own `bench cleanroom` window. Never wrap them in a script that starts runs and then checks on them, and never hand-write or poll a ledger or heartbeat; the receipts and `studio evidence launches` are the ledger.
- Run `studio host preflight` before the first launch. On Windows, stop with NEEDS-USER if it is not ready; elsewhere it reports `host_kind: unsupported`, which is recorded and does not stop the run.
- Performance is measured at the current scope in a `bench cleanroom` window before any refinement or scope expansion; a pass at a lower rung is never cited for a higher one.
- Never claim acceptance from exit codes, unit tests or source coverage; preserve failures and lead `RETURN.md` with player-facing metrics.
- The run commits nothing unless the production contract carries `snapshot_commit: authorized`. Under that line it commits once, at Return, to a new `run/<run-id>` branch, staging by name only the game files the run produced; no push, no merge, and the commit is a baseline for the user, never evidence of acceptance.
